# Text — charmap decoding & the game's variable formatting

Reference for `apricorn-core::text`, established in Phase 4 (step 2) by
decoding every one of the 49,984 retail messages in `a/0/2/7` and
cross-checking against pret/pokeheartgold's `src/pm_string.c`,
`src/message_format.c`, `src/string_control_code.c`,
`include/constants/charcode.h`, and `tools/msgenc/MessagesEncoder.cpp`.
**The retail image is the oracle**: the decoder is strict — every unit
must be a charmap character, a well-formed control-code block, or a
packed trainer name — and all 49,984 messages decode with zero
violations, reassembling byte-identically (`tests/text_hg.rs` pins the
census).

`formats::msg` (see `docs/nitro-msg.md`) decrypts a bank into raw u16
code units; this module turns units into text and substitutes the
game's display-time variables.

## The charmap

`charmap.rs` is **generated and committed**: a one-time codegen from
pret's `charmap.txt` (2,876 character entries + 16 command entries)
regenerated by

```sh
cargo run -p apricorn-tools -- gen-charmap \
    refs/pokeheartgold/charmap.txt \
    crates/apricorn-core/src/text/charmap.rs
```

The engine never depends on a local pret clone; `tests/charmap_hg.rs`
re-parses the source file with an independent parser and asserts the
committed table matches whenever the clone is present. Two codes are
dual-purpose — `0x0100` ('○' / `{STRVAR_1}`) and `0x0400` ('가' /
`{STRVAR_4}`): inside a `0xFFFE` block the code is the command; as a
plain unit it is the character (and as a plain unit neither occurs in
retail data).

Across the retail messages, 334 distinct units appear as plain
characters. The EN letter blocks: `0x12b`= 'A' (uppercase runs
`0x12b..0x144`), `0x145` = 'a' (lowercase `0x145..0x15e`), digits from
`0x121`, the space glyph is `0x1de` — the species-name bank (237)
therefore decodes as "BULBASAUR", not "Bulbasaur".

## Code-unit classes

| Units | Meaning |
|-------|---------|
| 0xFFFF | EOS, ends every message |
| 0xFFFE | ext control code: `code` (u16), `size` (u16), `size` field units |
| 0xE000 | linefeed (`CHAR_LF`), renders `'\n'` |
| 0xF100 | TRNAMECODE — a packed trainer-name block |
| else | a charmap character (`decode` rejects anything unmapped) |

**String variables** are the `0xFFFE` blocks whose `code & 0xFF00` is
0x0100, 0x0300, 0x0400, or 0x3400. The buffer index is **`field[0]`**
— the code's low byte is a tooling tag the game never reads (bank 0
message 10 uses one code with two different field values). Retail
census: 9,210 strvar blocks over 50 codes (34/9/3/4 codes per class),
always `size` 2 with `field[1]` == 0, `field[0]` ≤ 18. The other ten
control codes, all with a constant size:

| Code | Blocks | Size | | Code | Blocks | Size |
|------|--------|------|-|------|--------|------|
| 0x0200 | 738 | 1 | | 0x0205 | 233 | 0 |
| 0x0201 | 65 | 1 | | 0x0206 | 6 | 0 |
| 0x0202 | 37 | 1 | | 0xFF00 | 3,568 | 1 |
| 0x0203 | 34 | 1 | | 0xFF01 | 31 | 1 |
| 0x0204 | 3 | 1 | | 0xFF02 | 1 | 2 |

(13,926 `0xFFFE` blocks in total over 60 distinct codes — the same
count `tests/msg_hg.rs` pins by raw walk.)

## `GameString` — the game's `String` (`pm_string.c`)

Units, not bytes: every port keeps behavioral parity in u16 code-unit
space (`GameString` never stores the EOS; the C's invariant
`data[size] == EOS` is what the TRNAME walk leans on). `to_text` is a
**lossy debug rendering** through the charmap — the pret-text
serialization is tooling, not engine.

`String16_FormatInteger` is mirrored quirk-for-quirk: the C computes
`num / dividend` in *u32* arithmetic (the int operand converts), and
`num *= -1` overflows for `i32::MIN` — both reproduced via wrapping
u32 math, so even `i32::MIN` renders exactly as the retail binary
does (`-2147483648`). A digit ≥ 10 (field width narrower than the
number) renders as the JP question mark; `ndigits` must be 1..=10.

## Packed trainer names (TRNAME)

Trainer names are stored as 9-bit character codes packed LSB-first
into 15-bit units behind a `0xF100` marker — msgenc's space saving for
bank 729 (728 names, generated from `trainers.json`) and bank 246
(10 link-battle names: Don, Ed, Abby, …). 738 blocks, 3,355 span units
in total; every unpacked char stays in `0x12b..0x1de`.

Unpacking is the game's `String_Cat_HandleTrainerName`; packing is
msgenc's `EncodeMessage`. Two details matter:

- **Tail saturation.** The packer ORs `0xFFFF << bit` over the tail so
  the `0x1FF` terminator is always findable. A name whose bit length
  lands exactly on a 15-bit boundary (5, 10, … chars) emits *no*
  terminator unit — the unpacker then reads the message's EOS, which
  is all ones and completes the terminator.
- **Every block ends its message.** Retail TRNAME blocks are always
  message-final, which is what makes the EOS read legal; `decode`
  enforces it.

The walker returns the index it stopped at, and the C advances that
index *before* testing for the terminator — so when a terminator read
ends exactly on a unit boundary the index is one past the last unit
actually read. One consequence worth pinning: because the EOS unit is
all ones, every read window over it yields the terminator, so a
well-formed (EOS-terminated) message can never overrun its TRNAME
stream — `TrnameOverrun` is only reachable on truncated input.

## `MessageFormat` — placeholder expansion (`message_format.c`)

`StringExpandPlaceholders` walks a message and substitutes each strvar
block with its bound field (through `cat_handle_trainer_name`, so a
packed name field unpacks in place); every other control-code block
copies through verbatim. Retail fields go up to index 18 (the game's
default constructor makes 8).

The retail demo (pinned in `tests/text_hg.rs`): bank 3, message 3 is
Pound's usage line `<field 0> used\nPound!` — binding bank 237's
BULBASAUR expands to "BULBASAUR used\nPound!"; binding bank 729
message 261 (the packed "Blue") expands to "Blue used\nPound!". An
*empty* field substitutes nothing (the game does the same); an
out-of-range field index is the game's `GF_ASSERT`, an error here.
